# ClipForge Database Specification

This document defines the database, storage boundaries, relationships, indexes, migrations, security rules, and test requirements for the updated ClipForge platform.

The updated creator workflow is:

- Brands upload campaign source assets such as videos, logos, thumbnails, and reference documents.
- Those brand assets are stored in Cloudflare R2.
- Creators publish their clips on Instagram or YouTube.
- Creators submit the public Instagram or YouTube video link to ClipForge.
- ClipForge stores the submitted link, platform metadata, verification history, views, earnings, and moderation results.
- Creators do not upload video files to ClipForge.

---

## 1. Database Architecture

| Data area | Recommended service | Purpose |
|---|---|---|
| Application records | Cloudflare D1 / SQLite-compatible SQL database | Users, organizations, campaigns, submissions, links, views, earnings, payments, moderation, notifications |
| Large brand assets | Cloudflare R2 | Brand source videos, logos, thumbnails, reference images, and documents |
| Background processing | Cloudflare Queues or equivalent | Social metric sync, notifications, moderation jobs, payout processing, cleanup |
| Payments | Stripe or payment provider | Campaign funding, refunds, creator payouts, payment webhooks |
| Authentication secrets | Encrypted database fields or managed auth provider | Session hashes, encrypted social tokens, provider references |
| Analytics | D1 aggregates with optional analytics warehouse later | Campaign, submission, view, and earnings reporting |

### Storage boundaries

D1 stores:

- User and organization records
- Brand and creator profiles
- Campaign configuration
- Metadata for brand assets
- Instagram and YouTube submission links
- Platform post IDs and snapshots
- View verification records
- Earning ledger entries
- Payment and payout metadata
- Reports, notifications, audit logs, and webhook state

R2 stores:

- Brand source videos
- Brand logos
- Brand thumbnails
- Brand reference images
- Brand reference documents
- Optional campaign attachments

Do not store in D1:

- Creator-submitted video files
- Raw passwords
- Raw session tokens
- Bank account numbers or card numbers
- Large binary video content
- Unencrypted social access tokens

Creator submissions must not create creator media upload records. A submission is represented by a public Instagram or YouTube URL and its verified platform metadata.

## 3. Common Data Standards

### IDs

Use opaque string IDs with a resource prefix. Examples:

- usr_...
- org_...
- cmp_...
- sub_...
- ast_...
- snap_...
- led_...
- pay_...

IDs must be generated by the backend. The browser must never choose database IDs.

### Timestamps

- Store timestamps in UTC.
- Use ISO 8601 values at API boundaries.
- Use created_at and updated_at on mutable tables.
- Use append-only records for views, financial transactions, and audit events.

### Money

Store money as integer minor units:

- amount_cents = 1000 means 10.00 in a two-decimal currency.
- Always store currency separately.
- Never use floating-point values for balances or payments.

### JSON

Use JSON only for flexible, non-relational data such as:

- Campaign requirements
- Target countries
- Target languages
- Social links
- Provider response metadata
- Fraud signals
- Notification payloads

JSON fields must be validated with shared schemas before insertion.

## 7. Data Lifecycle

### Brand campaign assets

1. Create an asset metadata row with scan_status pending.
2. Generate a short-lived signed R2 upload URL.
3. Upload the brand asset directly to R2.
4. Verify file size, MIME type, checksum, and scan result.
5. Mark the asset clean or rejected.
6. When deleted, mark deleted_at before removing the R2 object.
7. Run orphan cleanup for failed or abandoned uploads.

### Creator submissions

1. Creator enters a public Instagram or YouTube URL.
2. API validates the URL and selected platform.
3. API extracts or verifies the platform post ID.
4. API stores the link and metadata in submissions.
5. Moderation checks eligibility and campaign rules.
6. A background job synchronizes views and engagement.
7. The submission remains represented by its URL and verification history.
8. ClipForge does not copy the creator video into R2.

### View data

- Store each provider observation as a new view_snapshots row.
- Keep the provider response hash for debugging.
- Never overwrite historical observations.
- Mark suspicious observations for review instead of silently deleting them.

### Financial data

- Earning ledger entries are immutable.
- Corrections are negative reversals or adjustment entries.
- Payment records are immutable except for controlled status transitions.
- Reconciliation jobs compare ledger totals with payment provider records.

## 8. Access and Security Rules

- Authenticate every protected request.
- Check organization membership on every organization resource.
- Check creator ownership on submissions, balances, and payout data.
- Moderators can access only assigned or permitted moderation queues.
- Admin actions require explicit admin authorization.
- Never trust role, organization ID, creator ID, or campaign ID sent by the browser.
- Query by authenticated ownership and server-side authorization.
- Use prepared statements or the ORM query builder.
- Validate all request bodies, query parameters, URL fields, and JSON fields.
- Rate-limit login, link submissions, report creation, and payout requests.
- Encrypt social tokens and sensitive provider references.
- Do not log passwords, tokens, signed URLs, or payment secrets.
- Add request_id values to logs and audit records.
- Audit every moderation decision, balance change, payout action, and permission change.

## 9. Required Database Tests

### Schema tests

- Migrations work on an empty database.
- Migrations work with seed data.
- Foreign keys reject invalid references.
- Unique constraints reject duplicate records.
- Required fields reject null values.
- Enum or status validation rejects unsupported values.
- Money fields reject negative values where not allowed.
- Timestamp fields use UTC.

### Creator submission tests

- Accept a valid Instagram public link.
- Accept a valid YouTube video or Short link.
- Reject unsupported platforms.
- Reject malformed URLs.
- Reject private, deleted, or inaccessible URLs.
- Reject duplicate campaign and platform post IDs.
- Store the normalized link and platform post ID.
- Do not create creator video asset records.
- Do not issue R2 upload credentials to creators.
- Store view snapshots from a verified provider.
- Handle a changed or deleted social post correctly.

### Brand asset tests

- Accept a valid brand source video or image.
- Reject an unsupported MIME type.
- Reject an oversized upload.
- Reject an unsafe filename.
- Store only R2 metadata in the database.
- Prevent unauthorized users from generating upload URLs.
- Prevent access after a signed URL expires.
- Mark failed uploads for cleanup.
- Prevent creators from uploading campaign assets.

### Earnings and payment tests

- Create an earning accrual from eligible views.
- Apply a campaign hold period.
- Release an earning after the hold period.
- Create a reversal without changing old ledger rows.
- Ignore duplicate earning events.
- Process a payment webhook only once.
- Reconcile ledger and payment totals.
- Prevent payouts for restricted payout accounts.
- Prevent spending beyond the campaign budget.

### Authorization tests

- A user cannot read another user's sessions.
- A creator cannot edit another creator's submission.
- A creator cannot access private brand assets without campaign eligibility.
- An organization member cannot access another organization.
- An analyst cannot change campaign budgets.
- A moderator cannot change payment balances without the correct permission.
- An unauthenticated request cannot access protected endpoints.

## 11. Definition of Done

The database implementation is complete when:

- A fresh environment can run all migrations successfully.
- The local seed command creates usable development data.
- Brands can create campaigns and store brand asset metadata for R2 files.
- Creators can submit public Instagram and YouTube links.
- Creator video files are never uploaded to ClipForge.
- Submissions do not contain a media_asset_id field.
- View snapshots are append-only.
- Earnings use an immutable ledger.
- Payment and webhook processing is idempotent.
- Organization and creator ownership rules are enforced.
- Required indexes and unique constraints exist.
- Schema, submission, asset, payment, authorization, and migration tests pass.
- API contracts and database documentation remain synchronized.
